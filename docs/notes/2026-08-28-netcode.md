# Netcode: the lockstep session

2026-08-28. The last item on the multiplayer list, and the only one that cannot
be finished inside this repo as it stands.

**What is built:** the transport-agnostic session, two working transports, the
wire protocol, divergence detection and reconnection-by-replay, with 33 checks
driving two complete Sessions against each other.

**What is not:** a transport that reaches another machine, and the integration
of every screen. Read §5 before assuming this is done.

---

## 1. Why it is small

Because the hard part was already built, two rounds ago, for other reasons.

This engine is deterministic by construction: every random draw goes through
`ctx.run.rng`, a seed reproduces a run exactly, `engine.choiceLog` records every
choice a player made and `setChoiceScript` replays them, and
`run._combatDigest()` already fingerprints **every seat's** board because a local
resume needed to verify itself. HANDOFF called that "a genuinely good base" and
it is: the session is ~300 lines because it is standing on all of it.

So the wire carries **INPUTS, NEVER STATE**. Nobody sends a board. Every client
applies the same ordered list of inputs to the same seed and computes the same
board — which is the only reason a Trick with a random effect works over a wire
at all. Sending state would be simpler for about a week and then every Companion
with an RNG call would desync.

## 2. The shape

```
  Transport            Session               Run / CombatEngine
  moves bytes    →     ordering,        →    knows nothing about
  knows no game        digests, rejoin       the wire
```

`net/transport.js` defines the interface and ships two that work today:

- **`LoopbackHub`** — several peers in one page, synchronous or asynchronous.
  This is what makes the netcode testable with no network, no build step and no
  second machine.
- **`ChannelTransport`** — `BroadcastChannel`, so two browser TABS are two
  genuinely independent game instances with real latency and real event-loop
  interleaving. Not the shipping answer (same origin, same machine) but a real
  wire, and it finds things a loopback cannot.

Steam P2P becomes a third file implementing the same five methods. Two rules are
written into the interface because lockstep cannot recover from either being
broken, and neither is free on a real transport: **order is preserved per
sender**, and **nothing is delivered back to its sender**. Steam has reliable and
unreliable channels; this traffic goes on a reliable ordered one.

## 3. The three things that go wrong

**Order.** Two players act at the same moment and the two clients apply their
inputs in different orders. Every input is stamped `(turn, seat, seq)` by its
author and applied in a total order sorted by exactly that — **seat index breaks
the tie, never arrival time**, because arrival time is the one thing guaranteed
to differ between two machines. Asserted by delivering the same pair of inputs
to two clients in opposite orders and checking both logs read `1.0.1 1.1.1`.

**Divergence.** Something non-deterministic slipped in. The board digest is
exchanged at turn boundaries and a mismatch is reported loudly, ONCE. A silently
divergent lockstep game is two people playing two different games while both
screens look fine, which is worse than a crash. Asserted by damaging one
client's enemy behind the other's back.

**Disconnection.** The designer asked for reconnection to shape the protocol
rather than be retrofitted, and it does: because the wire is an ordered input
log, a rejoining client asks for everything after what it has, replays it and
checks the digest — which is what `run._resumeCombat()` already does for a
player who quit and came back. Asserted by dropping a client, running two more
inputs without it, and catching it up from the log alone.

## 4. Two things building it found

### A card's `uid` is not a network identity

The first version of the protocol put `uid` on the wire. It looks completely
correct — unique, stable locally, round-trips cleanly. The remote client then
**failed to find the card and silently did nothing**: uids come from a counter
that runs per page, not per game, so two clients building their own engine from
the same seed produce the same cards in the same order with entirely different
uids (`c89` on one, `c109` on the other — the suite asserts exactly this).

The board drifts by one Trick and the digest catches it a turn later, a long way
from the cause. Cards are named by **position** now — `{ seat, pile, index }`
via `cardRef` / `refCard` — which is the identity lockstep already guarantees,
since both clients holding the same piles in the same order IS the premise. And
if they ever disagree about position they have already desynced, which is the
digest's job to say rather than a card lookup's job to hide.

This would have been much worse later: the initial decks would have matched by
luck of creation order, and only Companions that spawn cards mid-fight — Hush's
Contraband, Mopsy's Scrap, Brambleboo's Weeds, every one of Crinkle's Paper
Copies — would have broken it.

### Inputs must be applied strictly one at a time

`playCard` and `endTurn` are async: they animate, they await choices, they run
whole enemy phases. Firing input handlers as messages arrive lets two of them
interleave, and two clients that interleave differently compute different boards
from the same log. Not a crash — a desync several turns later.

Every input, local and remote alike, is now queued behind the last one, and
`session.settled()` is how a caller waits for the queue rather than for a guessed
number of milliseconds. This is also why `input()` does not apply anything
itself: there is ONE path into the game and it is ordered, so an ordering bug
shows up in a one-machine test instead of only over a real wire where it would
look like latency.

## 5. What remains — read this before calling it done

1. **A transport that reaches another machine.** Steam P2P per the designer's
   decision, which needs the wrapper shell and ends the no-build rule. One file,
   five methods, two rules.
2. **Routing every screen's actions through `input()`.** The protocol covers
   play / end / choice / snack / ready, and the test drives play and end against
   a real engine. The reward, Mr. Moth's, the Safe Room and Curiosity screens
   still act locally; each is a call site change, not a design question, and
   HANDOFF §9 already lists them with what each becomes.
3. **The choice broker reaching a remote picker.** `engine.choices.ask({ seat })`
   currently resolves another seat's request from its `prefer` rule. That
   fallback is deliberate and stays as the offline path; over a wire the request
   should reach that player's own picker and come back as `INPUT.CHOICE`.
4. **Lobby and seat assignment.** Who is seat 0, who hosts, how the seed is
   agreed. The session takes all three as constructor arguments today.

`shouldHandOff()` remains the single switch, and it already reads
`run.session && run.session.remote` — so a session with a real transport turns
off every pass-and-play veil in the game without touching any screen.

## 6. Verification

`tests/net/run.py` — **33 checks**, two complete Sessions over a loopback:

- the same seed deals both clients the same board, and each owns one seat
- an input crosses, lands in both logs exactly once, and both boards stay
  identical after it resolves
- a client cannot issue an input for a seat it does not own
- both clients agree on the order despite opposite arrival, and a late-arriving
  earlier turn still sorts into its place
- identical boards report no divergence; a drifted one is caught and reported
  once; a peer on a different seed is caught at hello, before a card is played
- a client that misses two inputs catches up from the log, in order, with
  nothing duplicated, and absorbing the same log twice adds nothing
- the same play over an ASYNCHRONOUS wire: nothing has arrived yet, it arrives
  on the next tick, both boards agree once it lands
- `BroadcastChannel` delivers to the other tab and never to the sender
